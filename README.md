# protobuf-javamin

A minimal protobuf-java replacement for tightly memory-constrained JVMs.

Drop-in for `com.google.protobuf:protobuf-javalite` at the API level (same class
shapes, same method signatures), but with a 50× smaller runtime and no per-class
lazy schema initialisation. Generated messages embed their read/write logic
inline — no `dynamicMethod` switch tables, no `MessageSchema` cache, no descriptor
table, no reflection.

## When to reach for this

You have a JVM running on a device that:

- has well under 200 MB total RAM;
- needs to encode/decode proto messages at steady state and cannot afford a
  metaspace climb during steady-state operation;
- doesn't need proto descriptors, reflection, or dynamic-message support.

In short: the constrained edge, not the server.

## Footprint vs alternatives

The runtime jar (the part that ships with your application) compared against
the official Google runtimes:

| Runtime | Jar size | Classes |
|---|---|---|
| `com.google.protobuf:protobuf-java:4.34.1` | 1.9 MB | ~660 |
| `com.google.protobuf:protobuf-javalite:4.34.1` | 1067 KB | 534 |
| **`dev.nemecec.protobuf.javamin:runtime`** | **20 KB** | **11** |

The runtime numbers above are repo-anchored: build it yourself.

Per-message generated bytecode is broadly similar to javalite's at the message
level (same Builder API surface), but **without** the lazy-initialised schema
machinery that adds ~10–20 KB of metaspace per message type as it's first
exercised. On a constrained device that's the difference between a flat
metaspace curve and a slow climb that eventually OOMs.

## Modules

- `:runtime` — the device-side jar. Zero runtime dependencies. The only thing
  your application classpath needs.
- `:codegen` — `protoc` plugin. Reads `CodeGeneratorRequest` from stdin and
  emits Java source files. Build-time only — does not ship to the device.
- `:integration-tests` — drives a sample `.proto` file through the codegen,
  compiles the generated Java against `:runtime`, and roundtrips messages.

## Wire compatibility

Byte-for-byte compatible with proto2 wire format. The `runtime` module's
`CodedOutputStreamCompatTest` and `CodedInputStreamCompatTest` pin this against
`com.google.protobuf:4.34.1` for every wire type plus boundary cases (varint
sign-extension, ZigZag, UTF-8 surrogate pairs, streaming-refill). If those
tests pass, anything you encode with this runtime parses on a peer using stock
protobuf-java, and vice versa.

## Use it

In your consumer's `build.gradle.kts`:

```kotlin
plugins {
  id("com.google.protobuf")
}

dependencies {
  implementation("dev.nemecec.protobuf.javamin:runtime")
}

protobuf {
  protoc { artifact = "com.google.protobuf:protoc:4.34.1" }
  plugins {
    id("javamin") {
      path = "<path-to-codegen>/build/install/codegen/bin/codegen"
    }
  }
  generateProtoTasks {
    all().configureEach {
      builtins.named("java") {}
      builtins.remove(builtins.named("java").get())
      plugins { id("javamin") }
    }
  }
}
```

The generated classes look like Google's `java_multiple_files = true` output,
except they import from `dev.nemecec.protobuf.javamin` instead of
`com.google.protobuf`. Existing call sites of the form
`MyProto.newBuilder().setX(...).build()` keep compiling once imports are
updated.

## Limitations

Deliberate omissions, in order of likelihood we'd add support:

- Proto3.
- `oneof`, `map<K, V>`.
- Packed repeated primitives (`[packed=true]` on the wire). Decoding falls
  through to skip-unknown-field.
- Extensions.
- `[default=...]` field defaults. Unset fields read back as the type default
  (0/""/empty).
- Reflection / `Descriptors` (defeats the point of being lean).
- Text format / JSON serialisation.

Behavioural notes vs `protobuf-javalite`:

- A duplicate singular message field on the wire is *replaced* (last-one-wins),
  not merged. proto2 spec says merge; in practice well-formed peers don't emit
  duplicates.
- `isInitialized()` checks only this message's required fields, not those of
  embedded message-typed fields. A top-level message is allowed through even
  if a (nested, optional) embedded message is missing some of *its* required
  fields.
- Generated messages override `equals` / `hashCode` / `toString` per field —
  two instances with the same fields compare equal regardless of set-order
  (no per-call allocation), and `toString` lists only the fields that are
  actually set (`Sample{id=1, name="x"}`).
- Builders don't expose `toBuilder()` or `Builder.mergeFrom(Message)`. Build a
  fresh builder if you need to copy.

Adding any of these is straightforward in the codegen and runtime if a need
arises.
